# 原生 CarWith：第三方 ARM 接收端实机基线

2026-09-30，在用户单独批准安装运行之后，`com.ucarhu.demo v1.2.2` 已在 Redmi K30 Pro / Android12 正常安装。**用户确认 HyperOS3 手机的原生 CarWith 已投到此接收端，应用投屏、可听音频、接收端触控操作正常。** 有限定范围的工具证据支持会话、呈现、音频播放器及触控发送活动；**DiPlay 自身尚未接入或取得原生首帧**。

这是两个普通安卓设备间的第三方软件接收成功组合，未使用外置连接盒。它解除了“该组合缺少可运行软件接收端”的可行性疑问；不能推广到任意手机版本、任意车机或不受限制的车端身份。

## 当前车辆名称与兼容白名单假设

用户明确要求考虑“可能必须是某些车辆名称”。将其保留为待验证假设，**不把换显示名当作已证实解法**。当前只证明此样本在其现有配置、名称和身份组合下能接收这一发送端。

可能影响接受的维度至少包括：显示车辆名称、厂商/产品标识、协议版本/能力、认证或配置身份。静态SDK中 `com.share.connect.Device` 同时有 `getVName/getVid/getPid/getCertServerId` 等方法；连接与认证模块又使用CCD配置、签名和证书消息。字段的存在不证明有白名单，也不证明车名只是自由UI文字。未读取CCD或秘密内容，更未把样本声明身份移植到DiPlay。

合法对照方案：取得SDK配置合同和获准测试身份后，先记录完整版本/配置类别及实际协议错误码；再只改变合同明确允许的显示名称，保持合法认证材料、厂商/产品ID与能力不变。若结果变化，再区分手机UI名称缓存和真实接入拒绝。身份/厂商/产品维度只能用获准的测试变体对照，不能克隆通过验证的车辆身份或绕过认证。当前连接保持原配置，本轮未做这些对照。

## DiPlay 下一步：从已运行样本到自主接收后端

实机证明了 **样本的ARM接收运行路径**；原“ARM能否加载/运行未知”的判断应限缩。当前缺口移到DiPlay集成所需的真实SDK合同、配置/合法身份来源、许可与兼容约束，而不是购买连接盒。

1. **取得可集成材料**：合法车端AAR/JAR/SO及依赖、版本/ABI、初始化与状态枚举说明、屏幕/音频/链路配置说明；明确测试与公开发布/再分发范围。APK成功不自动赋予复制其类/SO/配置的许可。独立实现则需足够的发现、认证与通道规范进行合法互操作，而非从函数名猜握手。
2. **确认身份与兼容合同**：CCD是什么、如何生成/提供合法测试配置、厂商/产品字段与车辆显示名哪些允许自定义、是否有准入/兼容列表、历史/新版CarWith的协商要求。当前“奇瑞风云2”必须计入这个调查；不沿用样本的身份。
3. **在DiPlay隔离debug后端接入实际API**：根据合同实现 `UCarAdapter.init → startAdvertise → 连接/认证回调 → startCast(Surface)`；绑定单Surface，处理旋转、暂停、断开/deInit和超时；并接入音频焦点/音频回传与touch/key边界。状态必须区分初始化、发现、正常配对、鉴权和首帧。SDK中相关API已静态确认，运行样本也证实了同APK本地连接服务；尚未编写猜测协议或导入未知许可SDK。
4. **先在ARM复现实机成功**：使用对应合法SDK/身份让手机发现DiPlay，完成正常配对/认证，取得DiPlay自己的第一帧，并验证触控与可听音频，再做断线重连。第三方APP成功不能代替这一验收。
5. **视频链路后再做性能验收**：当前K30Pro短Surface样本不是625级结果，既有x86 UI/fixture基准也不升级为原生性能。需要实际DiPlay视频参数、codec/队列/渲染时戳、持续帧和掉帧、CPU/内存及可测延迟。x86 SDK仍缺媒体ABI；真实ARM车机和模拟器分开测试。

本轮没有关闭原Project/Issues、改变原CarLife回退记录、合并或部署。**第三方原生CarWith兼容基线已有成功证据；DiPlay原生发现/鉴权/首帧仍待集成验收。**
